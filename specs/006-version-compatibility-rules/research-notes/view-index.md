# View index design (T069, FR-021, ADR-018 D-A7)

Status: design for T076/T077. Evidence: EV-540..EV-547 (one per pinned `odoo/odoo` revision), generated by
`tools/extract_view_index.py` from official sources at the pinned SHAs in `official_sources/revisions.json`.

## Purpose and rule semantics

Two DETECT_ONLY rules (shared step `*`, bound per run with the planned `target`):

- `*.xml.inherit-id-missing-in-target`: an `inherit_id` ref (`<field name="inherit_id" ref=...>`, `eval="ref(...)"`,
  `<template inherit_id=...>`) to a core module whose view id is absent from the target index. WARNING.
- `*.xml.xpath-anchor-missing-in-target`: a named anchor (`@name`, `@id` in an xpath predicate, or a shorthand
  element such as `<field name="x" position="after">`) absent from every core view of the parent's inheritance tree.
  WARNING, `review_required` (an anchor can be added by a non-core module).

Unverifiable is never an error and never proof of compatibility. INFO "Unverifiable: ..." is emitted when the
parent module is not a core module of the target, or when no index exists for the target ("index unavailable").
Refs without a module prefix and refs into scanned modules are skipped (the dependency integrity pass owns those).
Without a run `target` the binding skips the rule with an INFO gap (same mechanism as the version-prefix rule).

## Scope

- Source: `addons/<m>/` and `odoo/addons/<m>/` for the modules in the pinned `core_modules.json` (same SHAs).
- Files: only xml files named by the module manifest `data` key (literal dict, `ast.literal_eval`; nothing is
  executed). Files in `static/`, `tests/`, `i18n/`, `migrations/` and unlisted files are excluded. `demo` is excluded
  (views defined only in demo data do not exist in a normal database). An unreadable manifest falls back to all
  eligible xml files and is recorded in `problems` (none occurred at the pinned SHAs).
- Records: `<record model="ir.ui.view">` and `<template>`, wherever they appear in the listed files.
  Ids defined in `data/` files are therefore indexed the same way as ids in `views/` files (Odoo has no such
  distinction; QWeb templates of website/portal live in `views/` and `data/` alike).
- Ids are qualified `module.local`; an id already containing a dot keeps its own module.
- Not indexed: views created from Python, non-view records (actions, menus), `ir.ui.view` records of enterprise
  modules (not in the official `odoo/odoo` repository).

## Inherited-view chains

Each view stores the root of its inheritance tree (`""` = it is its own root; a parent outside the index also makes
a view its own root). Anchors are stored once per root as the sorted union of every `name=` and `id=` attribute value
in the arch of every core view of that tree (the `<attribute name=...>` edit elements are excluded). The union is
deliberately generous, so an anchor reported missing is missing from the root view, all its ancestors and all core
extensions: this is why a third-party anchor reported "missing" may be a false positive only when a non-core module
adds it, hence `review_required`. Anchors written as `%(module.action)d` are not compared (the parent may spell the
action id unqualified). `[@name='a' or @name='b']` is satisfied by either alternative.

## Size budget (agreed for D-A7)

JSON, one file per version under `compatibility/view_index/`, one line per module and per tree (diff friendly):
at most 1,000,000 bytes per version and 5,000,000 bytes in total (enforced by a test). Measured:

| version | modules | views | trees | anchors | bytes |
|---|---|---|---|---|---|
| 12.0 | 221 | 2842 | 1823 | 13202 | 374,813 |
| 13.0 | 259 | 3404 | 2054 | 15105 | 443,282 |
| 14.0 | 295 | 4073 | 2305 | 17081 | 519,078 |
| 15.0 | 325 | 4235 | 2563 | 19185 | 577,998 |
| 16.0 | 349 | 4594 | 2699 | 20885 | 638,877 |
| 17.0 | 413 | 5274 | 2896 | 22928 | 727,686 |
| 18.0 | 451 | 5789 | 3138 | 24170 | 786,642 |
| 19.0 | 450 | 5916 | 3291 | 24703 | 804,738 |

Total 4,873,114 bytes (about 0.6 MB gzipped per release in a wheel). Restricting to "views relevant to scanned
modules" is not possible at build time (the scanned modules are unknown), so the index covers all core views with ids
and anchors only; no arch text, no attribute values, no line numbers.

## Provenance and reproducibility

Each index records `version`, `repository`, `revision`, `evidence`, `tool`, `scope`, `counts`, `problems` and
`content_sha256` (over `views` and `anchors`). `fetch` downloads raw files at the pinned SHA into a cache (module list
from the pinned core list; the SHA must agree with it), `extract` parses the cache offline. Output has sorted keys, no
timestamps and a fixed layout; a test builds it twice and compares bytes. EV-540..547 cite the SHA, the tool and the
content hash. Pinned core lists, evidence and view indexes thus share one revision per series.

## Coverage estimate (measured by running the detectors over official core files)

Same-version self-check (each version's core view files against its own index; any finding would be a false
positive): 0 inherit-id findings and 0 xpath findings for all eight versions (12.0..19.0), 0 "unverifiable". The first
19.0 run found 4 false positives from `@name='journal_line_ids' or @name='line_ids'`; the `or` handling above fixed
them. This is partly self-referential (the anchor union includes the checking view), so it bounds false positives, not
recall.

Previous-series core files against the next series index (real vanished refs/anchors, the rules' hit rate; WARNING
counts, then INFO unverifiable): 

| step | inherit-id | xpath anchor |
|---|---|---|
| 12-13 | 51 / 12 | 95 / 16 |
| 13-14 | 25 / 0 | 55 / 0 |
| 14-15 | 395 / 4 | 63 / 1 |
| 15-16 | 51 / 23 | 72 / 22 |
| 16-17 | 58 / 1 | 76 / 1 |
| 17-18 | 4 / 1 | 88 / 2 |
| 18-19 | 168 / 17 | 145 / 18 |

Core modules are removed or renamed between series, so many of these are genuine (for example 15.0
`payment.payment_acquirer_form`, EV-450, absent from 16.0). They are not individually triaged here; these counts show
the rules fire on real change and that the index resolves core refs (unverifiable stays under 10 percent of findings
except where core modules were removed). Golden check (T077): `payment.payment_acquirer_form` is a WARNING at targets
16.0 and 17.0.., absent finding at 15.0, as EV-450 records.

## Limits (stated, not hidden)

- Verified only: ids/anchors of the official `odoo/odoo` repository at the pinned SHAs. Enterprise views and custom
  modules are unverifiable by design.
- A missing `name`/`id` anchor does not prove the xpath fails (class or positional xpaths are not checked) and a present
  one does not prove the xpath still matches the same node.
- No fix is offered; renamed-view mapping is not inferred without authoritative evidence (see D-A5 for models).
- Packaging: `pyproject.toml` package-data currently lists only `knowledge/*.json`; shipping the index (and the other
  `compatibility/` data) in a wheel needs that list widened (outside this task's ownership, flagged for the owner).
